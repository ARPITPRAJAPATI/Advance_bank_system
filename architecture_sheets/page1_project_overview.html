WHAT KUBEPAY SOLVES
🔁 Silent Double-Debit (Race Condition) Network retry or accidental double-click triggers two concurrent debits. Solved via client-side UUID idempotency keys enforced by DB TTL index — duplicates replay the same response without touching balances.
📒 Silent Balance Corruption Single-column balance fields can silently corrupt under concurrent DB writes. Solved via immutable double-entry ledger: Balance is always computed as Σ(CREDIT) - Σ(DEBIT) — no raw balance column in DB.
🤖 Unchecked Autonomous AI Money Movement Prompt injection attacks can instruct AI agents to bypass financial checks. Solved via HITL: AI can only prepare transfers — a cryptographically signed, 5-minute expiry token ensures humans authorize every rupee movement.
🔒 Manual, Error-Prone Deployments Developers kubectl apply directly to clusters with no audit. Solved via GitOps: GitHub is the single source of truth; ArgoCD self-heals; Jenkins CI enforces security gates before any image reaches EKS.

KEY DESIGN DECISIONS
Why Double-Entry Ledger? Any loss of a single rupee is traceable from day 1. Sum of all DEBITs must equal sum of all CREDITs. Nightly reconciler enforces this invariant automatically.
Why GitOps over Direct Deploy? Direct kubectl requires cluster credentials inside CI agent. ArgoCD inverts control — cluster pulls from Git — with zero external credentials exposure.
Why HITL for AI Transfers? LLMs are probabilistic; a prompt injection could trigger unintended transfers. HMAC-signed tokens ensure no money moves without an explicit human approval click.
Why Idempotency at Two Layers? Client UUID prevents duplicate HTTP replays. MongoDB session prevents concurrent race conditions. Both are needed for real-world reliability.
Why Controller-Worker Jenkins? Master node stays lightweight (scheduler only). Build side-effects, Docker socket access, and security tool binaries are isolated to the dedicated worker agent.
